## Verdict / 结论

All three previous items (`json_encode` failure, `id:null` treated as a notification, exception message leakage) are fixed, and fixed well. But the **new encoding fallback only thinks about a single request**, and it breaks the batch path in the process.

上一轮的三项（`json_encode` 失败、`id:null` 当通知、异常信息泄露）都已修好，且修法得当。但**新修好的编码兜底只考虑单请求**，批量路径反而被它带坏。

## P0

### P0-1

- **Status / 状态**: Open
- **Where / 位置**: `src/JsonRpcServer.php:179` → `:249-258`
- **Verification / 验证**: reproduced
- **EN**: In a batch request, if any single result cannot be `json_encode`d (say a handler returns invalid UTF-8), the whole response collapses into a **single error object** instead of an array, and every valid result is lost — violating the JSON-RPC requirement that a batch response must be an array[4]
- **中文**: 批量请求中若任一条结果无法 `json_encode`（如 handler 返回非法 UTF-8），整个响应退化成**单个错误对象**而非数组，全部有效结果丢失，违反 JSON-RPC 批量响应必须为数组的规范[4]

### P0-2

- **Status / 状态**: Open
- **Where / 位置**: `src/JsonRpcServer.php:195-196` and `:145`
- **Verification / 验证**: reproduced
- **EN**: A legal empty named-parameter object `params:{}` is judged by `array_is_list([])` to be empty positional parameters, so the handler is called with zero arguments, throws `ArgumentCountError`, returns `-32603` and ships the PHP exception class name back in `data`
- **中文**: 合法空命名参数对象 `params:{}` 被 `array_is_list([])` 判成空位置参数，处理器 0 参调用抛 `ArgumentCountError`，返回 `-32603` 并把 PHP 异常类名放进 `data` 回传远端

## P1

### P1-1

- **Status / 状态**: Open

- **EN**: The README's "integration with miGears Web" example calls two methods that do not exist: `$this->service('rpc')` (the correct web-side method is `resolve()`) and `$request->getBody()` (web's `Request` only has the public property `$body`). Copying it is a fatal error

## P2

### P2-1

- **Status / 状态**: Open
- **Where / 位置**: `src/JsonRpcServer.php:249-258`, `src/JsonRpcClient.php:67`
- **Verification / 验证**: reproduced
- **EN**: When a single request's result cannot be encoded, the response loses the original `id` (it returns `id:null`), so the client surfaces an "id mismatch" rather than the real error; and the client compares `$data['id'] !== $id` strictly, so a server that echoes an integer id as a string is misreported as a protocol error
- **中文**: 单请求结果无法编码时响应丢失原始 `id`（回传 `id:null`），客户端会以「id mismatch」而非真实错误呈现；客户端 `$data['id'] !== $id` 严格比较，服务器把整数 id 回显成字符串就误判为协议错误

### P2-2

- **Status / 状态**: Open
- **Where / 位置**: `src/JsonRpcClient.php:186,200,204-212`
- **Verification / 验证**: reproduced
- **EN**: `notify()` ignores the configured timeout and hardcodes 0.5 seconds, and swallows every error with `@` and returns silently; the waiting path rebuilds error text from `error_get_last()`, which can pick up a stale unrelated error
- **中文**: `notify()` 忽略构造器 timeout 并硬编码 0.5 秒，且用 `@` 吞掉全部错误静默返回；等待路径靠 `error_get_last()` 拼错误信息易取到陈旧错误

## Test gaps / 测试盲区

Test gaps: the encoding fallback is only tested for a single request; nothing covers one un-encodable result inside a batch; nothing covers `params:{}`; no interop test where the server normalises the id to a string; `testNotifyDoesNotThrow` only asserts it does not throw, not that it honours the timeout.

测试盲区：编码兜底只测了单请求；无批量中单条不可编码用例；无 `params:{}` 用例；无「id 被服务器归一化为字符串」的互操作用例；`testNotifyDoesNotThrow` 只断言不抛，未断言是否遵守 timeout。
