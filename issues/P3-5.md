# P3-5 — The `\TypeError` catch added for parameter binding is too broad: a …

## Finding / 问题

- EN: The `\TypeError` catch added for parameter binding is too broad: a `TypeError` raised inside a handler is reported to the caller as `-32602 Invalid params`, blaming the remote caller for the server's own defect. The fix is to narrow the catch to the binding step.

- 2026-10-01 · `maintainer — migears` · `fixed` — `fixed`. The `\TypeError` catch is gone from `handleSingle()` (`src/JsonRpcServer.php:151-154`), and the argument list is now judged before the call instead: `callHandler()` builds the arguments, passes them through `assertArgumentsBind()` (`:255-295`) and only then calls the handler. A `TypeError` raised inside a handler's body is therefore no longer caught, so it falls to the generic handler and arrives as `-32603 Internal error` with `TypeError` in `data`, which is where the server's own defect belongs. The pre-check mirrors PHP's own rules rather than a simpler set of its own, so it never refuses an argument list PHP would accept — that is what keeps `-32602` exactly where it was for the caller's mistakes. Two properties of this call site make that possible: `JsonRpcServer.php` declares `strict_types`, so no scalar is coerced on the way in (probed: `int $a` refuses `'5'` and `1.0`, accepts only `int`), and the values can only be the kinds `json_decode` produces, so `argumentFits()`/`namedTypeFits()` (`:297-360`) decide each declared type exactly. The finding's own text said the fix was to narrow the catch to the binding step; this does that one better by removing the need for the catch at all, because a narrowed catch is not reachable in PHP — the body runs inside the same `try`. Pre-checking the count alone was the other candidate and would have left the type half unjudged; judging types by a rule set of its own was the one risk worth avoiding, since refusing what PHP accepts is the same class of mistake as this item. `tests/JsonRpcServerTest.php:222` and `:239` pin the two body shapes (a direct `throw` and a typed call one level down), `:263` pins the internal-function argument-count case, and `:280` pins that a user function's extra argument is still tolerated, which is the half of that asymmetry that must not be tightened. Putting the broad catch back turns `:222` and `:239` red with `-32602` against `-32603`; dropping the `int` rule turns the pre-existing `testParamTypeMismatchReturnsInvalidParams` red with `-32603`, which is what shows the checker is what holds `-32602` in place. 61 tests / 134 assertions green and `phpstan` level 6 clean over `src` and `tests`. README states the split in both halves (Behaviour Notes). The fix is in the working tree and not in `HEAD`; no reviewer verdict exists for it yet.
